# 命名と識別子

## 基本方針

AWSコンソールで所属を判別できる共通の技術名をconfigへ1つ置き、サービス別の文字種・長さ・区切りへの変換はCDK側へ集約する。表示名は技術名と分ける。

```json
{
  "defaultCdkPrefix": "Example-System_Dev",
  "runtimeDisplayName": "サンプルAI"
}
```

キー名は例であり、既存プロジェクトの語彙を優先する。同じ意味の小文字版、アンダースコア版、スラッシュ版、ハッシュ版を利用者に列挙させない。

## 4種類の識別子を混同しない

| 種類 | 用途 | 安定性の扱い |
|---|---|---|
| Construct ID | CDK Construct tree内の識別子 | パス変更がLogical IDを変え得るため、見た目だけを理由に変更しない |
| CloudFormation Logical ID | Stack内でCloudFormationがリソースを追跡するID | 既存リソースでは変更前後をsynth/diffで確認する |
| Physical name | AWSサービス上の実名 | 外部契約や人間の識別に必要な対象だけ明示し、可能ならCDK生成へ任せる |
| アプリケーション名前空間 | 費用、Memory、テナント等のデータキー | リソース物理IDへ安易に連動させず、移行要件を別途判断する |

AWS CDKはConstruct pathからLogical IDを生成し、通常は可読部分と8文字ハッシュを使う。Constructの移動やID変更は、コード上のリファクタリングでもCloudFormation上の別リソースとして扱われる可能性がある。

## 物理名の判断

- コード内参照だけで足りるリソースは、CDK生成名とtoken参照を優先する。
- DNS名、Cognito提供ドメイン、外部連携先が参照する名前など、名前自体が契約になる対象だけ明示を検討する。
- 明示名が置換を妨げることを前提にdiffを確認する。同じ名前の新旧リソースを同時作成できないサービスがある。
- Stack名へ共通名を反映すれば補助リソースの自動生成名でも所属を判別できる場合、個別の物理名を増やさない。
- AWS発行IDやサービス管理ログの既定パスなど、制御できない名前は例外として記録する。

## 正規化

- 前後空白、連続区切り、大小文字、許可文字、先頭文字、最大長を対象サービスごとに検証する。
- 長さ短縮が必要なら、用途の接尾辞と一意性を含む最終名を基準にする。
- 一意性用識別子は、同一Stackの更新で安定する材料を使う。synthごとの乱数を使わない。
- アカウント、リージョン、基準名から独自ハッシュを常に作る設計を既定にしない。CDK/AWS生成名で解決できる場合は任せる。
- 競合時に勝手な別名へフォールバックせず、対象と原因を示す。

## 個別設定に残すもの

表示名、所有済みカスタムドメイン、証明書、Hosted Zone、外部Secret、既存Knowledge Baseなどは共通名から推測しない。外部所有物と既存データの継続性は命名変換と別の問題として扱う。

## 確認項目

- 共通名1か所から所属を判別でき、変換済み名称の二重管理がないか。
- 表示名だけの変更で物理名やデータキーが変わらないか。
- Construct IDの変更によるLogical ID差分がないか。
- 明示した物理名が更新・置換・並行環境を妨げないか。
- 自動生成名、補助リソース、命名不能な例外までsynthで確認したか。
